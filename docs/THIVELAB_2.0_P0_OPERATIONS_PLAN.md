# THIVELAB 2.0 — P0 운영 보호 실행안

작성: 2026-10-09 KST. [P0 검증 결과](./THIVELAB_2.0_P0_READINESS.md)의 미완료 항목에 대한 **준비 문서**다. 아래 운영 전환·복원·백업·경보는 실행하지 않았다. 기존 운영 코드·DB·Cloudflare·Caddy·PM2·launchd 설정과 공개 배포는 변경하지 않았다.

## 1. 운영·DEV 소스 및 빌드 분리

**현재 FAIL:** PM2의 `thivelab-web`(`next start`, 3103)과 `thivelab-dev`(`next dev`, 3104)가 모두 `/Users/mainthive/project/ai-blog`를 작업 경로로 사용한다. `.next` 하위 디렉터리가 나뉘어도 소스 checkout과 빌드 대상은 공유된다. `docs/SELF_HOST_CLOUDFLARE.md`의 현재 빌드 안내를 이 경로에서 실행하면 운영 영향 가능성이 있다.

**승인 후 전환안:**

1. `~/project/nodelog-dev`를 별도 checkout/worktree로, `~/project/nodelog-releases/<commit>`을 운영 릴리스별 별도 checkout으로 둔다. 두 디렉터리의 `node_modules`, `.next`, `.env`/비밀 파일을 공유하지 않는다. 기존 `ai-blog`를 복사해 운영 릴리스로 쓰지 말고, 배포할 commit과 의존성 lockfile을 고정한다.
2. 릴리스 후보는 운영 경로가 아닌 별도 릴리스 디렉터리에서 설치·빌드한다. 해당 디렉터리에서만 로컬 전용 후보 포트를 띄워 홈, 핵심 URL, 댓글·구독 등 필요한 쓰기 동작, canonical·sitemap·redirect를 검증한다. 후보가 현재 DB에 연결하면 쓰기 E2E는 격리 DB에서만 수행한다.
3. 릴리스 경로를 PM2가 참조하도록 바꾸는 단계는 별도 유지보수 창·승인 대상이다. 전환 직전 현재 PM2 설정, commit, 환경 변수 **키 목록만**, SEO 기준선과 DB 덤프 식별자를 기록한다. 비밀 값은 기록하지 않는다.
4. 전환 후 3103 응답, 프로세스 안정성, 핵심 URL, 저장 기능을 확인한다. 실패하면 보존한 **이전 릴리스 경로와 프로세스 설정**으로 되돌리고 같은 표본을 재검증한다. 롤백 리허설 결과가 없으므로 현재는 운영 전환 NO-GO다.
5. DEV 3104도 별도 checkout으로 옮긴 뒤 운영 디렉터리와 빌드 산출물을 참조하지 않는지 PM2 cwd, 실제 PID cwd, 파일 경로로 재검증한다. 공개 DEV 접근 정책은 Cloudflare/방화벽 권한 확인 후 결정한다.

## 2. 최신 DB 덤프 격리 복원 시험 준비

**현재 NOT VERIFIED:** 2026-10-09 04:17 KST의 `nodelog-20261009-0417.dump`는 5.4MiB이고 기존 백업 절차에서 `pg_restore --list`의 `public` TABLE DATA 6개를 확인했다. 이는 실제 복원·읽기 성공의 증거가 아니다. `nodelog-globals.sql`도 같은 백업 디렉터리에 있다. 아래 절차는 새 격리 컨테이너·새 볼륨·루프백 전용 포트가 준비된 뒤 승인 하에 실행한다.

1. 원본 덤프와 globals 파일의 SHA-256, 생성 시각, `pg_restore --list`, 예상 schema·테이블 목록을 **기록만** 한다. 복원 작업자는 덤프에 개인정보가 있을 수 있으므로 출력·로그·테스트 결과에 실제 행 값을 남기지 않는다.
2. 운영 Docker 네트워크·볼륨·DB 컨테이너 이름과 겹치지 않는 일회성 PostgreSQL 17 격리 환경을 만든다. 외부 인터페이스에 포트를 공개하지 않는다. 프로덕션 DSN/비밀번호를 격리 환경에 넣지 않는다. 확장(`vector` 등)과 복원에 필요한 역할·함수를 운영 README의 2026-09-29 기록 및 실제 덤프 TOC에 맞춰 검토한다.
3. `nodelog-globals.sql`에 비밀번호는 없지만 역할 생성 SQL이므로 **격리 DB에만** 적용한다. 새 빈 DB에 덤프를 `pg_restore --exit-on-error --no-owner` 방식으로 복원한다. 누락 확장·권한 오류는 성공으로 묵살하지 않고 원인을 기록한다.
4. 테이블·인덱스·제약·함수 목록, 6개 public 테이블의 `count(*)`, 주요 읽기 쿼리, 앱이 기대하는 인증 함수와 권한을 확인한다. 동일 시점 운영 행 수와 일치 여부는 덤프 시점 차이를 고려한다. 읽기 시험은 격리 환경의 가짜 자격 증명으로만 한다.
5. 복원 시간, 실패/성공 단계, dump checksum, 검증 SQL과 **값을 제외한 결과**를 기록한다. 시험 데이터를 안전하게 폐기하고 볼륨·컨테이너가 제거됐는지 확인한다. 분리된 시험에서 운영 트래픽·DB 연결 변화가 없었는지 확인한다.

## 3. 외부 백업 설계

**현재 FAIL:** `nodelog-backup.sh`는 매일 로컬 덤프를 만들지만 `OFFSITE_DEST`가 비어 있다. 이 옵션은 디렉터리로 `cp`만 하며 `nodelog-globals.sql`은 복사하지 않는다. 대상이 없으면 경고를 남기고 작업은 성공으로 끝날 수 있다. 같은 Mac에 연결된 디스크만으로는 Mac 분실·장애 시 복구를 보장할 수 없다.

**승인 후 권장 구성:** Mac 외부의 접근 통제된 저장소(예: 암호화된 원격 오브젝트 저장소 또는 별도 장소의 백업 장치)를 선정하고, 전송 전 암호화·키 관리·최소 권한·버전 보존·삭제 보호를 정의한다. 덤프와 globals를 함께 복사하고 SHA-256 대조와 실패 시 별도 경보를 수행한다. 비밀번호·토큰을 plist나 문서에 쓰지 않는다. 현행 로컬 14개 보관과 외부 보존 기간은 실제 용량·복구 목표·개인정보 보존 정책을 확인한 뒤 정한다. 첫 사본 전송이 아니라 **외부 사본만으로 격리 복원 성공**을 완료 조건으로 한다. CIPHER·MOA는 백업 범위와 복원 결과를 별도로 확인한다.

## 4. 로그 증가와 디스크 경보

**확인된 원인 범위:** PM2 `blog-approval`은 stopped 상태이고 재시작 카운터가 약 3,913만이다. PM2의 실행 경로 `/Users/mainthive/project/SAFESUARE/backend/telegram_approval_bot.py`가 현재 존재하지 않는다. 회전된 `blog-approval-error` 표본에 Python의 `can't open file ... [Errno 2]`가 반복된다. 이 반복이 해당 오류 로그 증가의 직접 원인이다. PM2 전체 로그 729MiB, `ai-blog/.next` 2.7GiB, 데이터 볼륨 가용 49GiB·사용률 89%를 관측했다. 이 숫자는 시점값이며 전체 로그 증가의 모든 원인을 조사한 것은 아니다.

**승인 대상:** `blog-approval`이 아직 필요한 기능인지 운영 담당자가 먼저 판정하고, 필요한 경우 코드 경로·실행 파일·재시작 정책을 복구한다. 불필요한 경우 설정에서 제거하기 전에 관련 알림/승인 기능의 종속성을 확인한다. 오래된 로그의 보존·삭제는 개인정보/장애 분석 필요성과 백업 여부를 확인한 뒤 진행한다. 지금은 서비스 변경·로그 삭제를 하지 않는다.

**경보안:** 데이터 볼륨 사용률 85% 및 가용 40GiB 아래에서 경고, 90% 및 25GiB 아래에서 긴급 알림을 시작값으로 제안한다. 둘 중 하나라도 충족하면 발송한다. PM2 로그 총량 1GiB, 단일 로그 증가 100MiB/일, 백업 덤프 누락/검증 실패, 외부 복사 실패를 별도 신호로 둔다. 초기 2주간 변화량을 확인해 임계값을 조정한다. 경보는 메일 등 **기존 운영자가 확인하는 채널**과 수신 확인 절차를 정해야 하며 현재 구현되지 않았다.
