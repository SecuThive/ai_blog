# THIVELAB 2.0 — B2C 사업 전략 보완안

기준: 2026-10-09. [현황 진단](./THIVELAB_2.0_AUDIT.md)과 [기술 로드맵](./THIVELAB_2.0_ROADMAP.md)을 함께 읽는다. 이 문서의 **MVP 도구 목록이 기술 로드맵 §1의 원안 목록보다 최신 결정안**이다. 기술 로드맵의 운영 보호(P0), 별도 앱·환경 분리, 기존 URL·SEO 보존, 테스트·롤백 게이트는 그대로 적용한다. 현재는 설계만 한다. 운영 코드, DB, DNS, Cloudflare 설정 및 배포를 변경하지 않는다.

## 1. 고객과 서비스의 역할

| 서비스 | 우선 고객·방문 목적 | TOOLS와의 관계 | 현재 확인 범위 |
| --- | --- | --- | --- |
| THIVELAB 메인 | 여러 서비스를 찾는 방문자 | TOOLS의 존재와 주요 작업을 명확하게 안내 | 메인 사이트에 현재 TOOLS 메뉴·호스트는 없음. 신규 진입 영역은 계획 |
| NODELOG | 기술 문제를 이해하거나 해결하려는 독자 | 이미지·PDF·텍스트 작업과 실제로 관련된 글에서만 도구로 연결; 도구는 해설 글로 역링크 | 현재 기술 콘텐츠와 검색 경로 운영 중. 관련 글의 실제 적합성은 편집 검토 필요 |
| CIPHER | 기술 학습·실습 이용자 | 기존 학습 목적 유지. 소비자 파일 변환 도구와 억지로 연결하지 않음 | 별도 서비스 운영 확인, 고객 행동 자료는 미확인 |
| MOA | 별도 서비스 이용자·조직 고객 | 기존 목적·계정·데이터 경로 유지. 공통 브랜드 외 B2C 전환 대상 아님 | 별도 앱 운영 확인, 실제 고객 구성·매출은 미확인 |
| 신규 TOOLS | 휴대전화·PC에서 파일 하나를 빨리 변환하거나 문서 작업을 마치려는 일반 이용자 | 한 가지 작업을 설명→선택→로컬 처리→다운로드까지 끝내는 독립 앱 | 수요·반복 사용·수익성은 가설. 출시 후 측정 필요 |

**가치 제안 가설:** 설치와 회원가입 없이 브라우저에서 작업하고, 사용자 파일이 서버로 전송되지 않는다는 점이 사용 이유가 될 수 있다. 이 장점이 실제 검색 유입·완료율·재방문으로 이어지는지는 아직 입증되지 않았다. 파일의 브라우저 처리 과정에서 사용하는 라이브러리, 분석 요청, 향후 광고 요청은 별도로 정확히 고지한다.

## 2. 소비자용 무료 MVP: 6개 도구

도구마다 고유한 작업·지원 범위·실패 조건을 갖는다. 아래 순서는 **개발 및 사용성 검증 우선순위 제안**이며 검색량 순위나 매출 예측이 아니다. 한 도구의 공통 파일 처리·접근성 부품을 다음 도구에 재사용한다.

| 순서 | 도구·예상 URL | 가장 짧은 사용자 과업 | 무료 범위·초기 검증 |
| --- | --- | --- | --- |
| 1 | 이미지 크기·용량 조절 `/image/resize` | 사진의 가로·세로 또는 품질을 지정해 저장 | 한 이미지의 전후 픽셀·바이트 크기 표시. JPEG/PNG/WebP, 투명도·색상 프로파일·EXIF 손실과 브라우저 지원을 실제 파일로 검증 |
| 2 | 이미지 형식 변환 `/image/convert` | 지원 형식의 이미지를 다른 형식으로 저장 | 지원되는 입력·출력만 선택 가능. 투명 배경→JPEG 배경 처리, 애니메이션·HEIC·AVIF 등 미지원 또는 제한 범위를 명시 |
| 3 | 글자 수 세기 `/text/count` | 입력·붙여넣기 텍스트의 길이를 즉시 확인 | 공백 포함/제외 글자 수, 줄 수와 단어 수를 명확히 구분. 한글·이모지·조합 문자 계산 기준과 브라우저 차이를 시험. 입력은 URL·로그·분석에 넣지 않음 |
| 4 | 이미지→PDF `/pdf/from-images` | 사진 여러 장의 순서를 정해 PDF 한 개로 저장 | 페이지 크기·방향·여백 또는 원본 비율 중 검증 가능한 선택지만 제공. 회전·비율·해상도·파일 크기·메모리 실패를 시험 |
| 5 | PDF 합치기 `/pdf/merge` | 여러 PDF의 순서를 정해 하나로 저장 | 암호화·손상 PDF, 페이지 순서, 합계 크기 제한과 오류 처리 시험 |
| 6 | PDF 페이지 추출 `/pdf/extract` | 지정한 페이지를 새 PDF로 저장 | 범위·중복·역순·없는 페이지·암호화 파일의 동작을 정의하고 시험 |

순서 3은 구현 비용이 낮아 사용성·분석 계측의 초기 연습에 적합하다는 **추론**이다. 순서 4~6의 PDF 작업은 파서·메모리와 모바일 브라우저 한도가 변수다. 초기 제안 한도(파일당 25MiB, 작업당 100MiB, 20개, PDF 200페이지)는 기술 로드맵의 시험용 값이며, 저사양 장치 시험 후 지원 범위를 공개한다. 한도는 브라우저 안정성을 위한 것이고 유료 전환을 위해 의도적으로 낮춘 수치가 아니다.

### 원안에서 바뀐 점과 테스트 영향

| 원안 | 이번 결정 | 설계·회귀 시험 변경 |
| --- | --- | --- |
| `/text/diff` 텍스트 차이 비교 | MVP 제외, 후속 **Developer Tools** 후보 | 긴 텍스트 diff 알고리즘·하이라이트·성능 fixture는 MVP 필수 게이트에서 제거. URL·메뉴·검색 노출을 출시하지 않음 |
| `/text/json` JSON 검사·정렬 | MVP 제외, 후속 **Developer Tools** 후보 | JSON 문법·정렬 fixture와 관련 이벤트를 MVP 필수 게이트에서 제거. 사용자 수요 조사 후 결정 |
| 신규 `/pdf/from-images` | MVP 추가 | 이미지 디코드→PDF 페이지 생성, 사진 순서·방향·비율·해상도·다중 이미지, 손상 이미지·메모리 초과·취소·다운로드 시험 추가 |
| 신규 `/text/count` | MVP 추가 | 공백·개행·한글 조합·이모지·긴 입력·붙여넣기·복사 시험, 글자/단어/줄 계산 정의 추가. 민감한 입력이 분석·URL에 섞이지 않는지 확인 |
| 기존 이미지/PDF 4개 | 유지 | 공통 파일 선택, 크기·형식 한도, 오류 상태, Blob URL 정리, 모바일·키보드 시험 유지 |

기술 로드맵 §7의 자동화 게이트에 적힌 `diff·JSON 출력`은 이 MVP에서는 `이미지→PDF 결과 페이지·순서`와 `글자 수 계산`으로 대체해 실행한다. 기존 NODELOG 테스트·SEO 기준선은 바뀌지 않는다. 후속 Developer Tools를 만들 때는 별도 수요 검증과 범위 결정이 필요하다.

## 3. 무료와 유료의 경계

| 단계 | 제공 후보 | 비용·권한 원칙 |
| --- | --- | --- |
| **현재 MVP: 무료** | 위 6개 도구의 핵심 작업, 설명·다운로드. 회원가입·파일 업로드 없음 | 브라우저 안에서만 처리. AI API, 사용자 파일 저장, 새 DB, 결제, 광고 SDK를 넣지 않음 |
| **후속 무료 후보** | 처리 이력 없이 다시 쓰는 프리셋, 더 넓은 형식 지원, Developer Tools의 diff·JSON | 실제 이용 요청·브라우저 비용을 측정한 뒤 선택. 지원하지 않는 형식에 빈 URL을 미리 만들지 않음 |
| **향후 유료 가설** | 반복적인 일괄 처리의 작업 템플릿·고급 옵션·팀 사용성 | 무료 핵심 작업을 없애는 계획이 아님. 브라우저 메모리 한도를 넘는 대량 작업은 서버 처리·결제·개인정보 설계 전에는 약속하지 않음 |
| **향후 AI 가설** | 문서 요약·정리 등 명시적으로 요청한 부가 작업 | 별도 AI Cost Gateway, 인증, 사용량·비용 상한, 결제/환불, 민감 정보 처리·삭제 정책과 동의가 준비된 뒤 실험. 현재 MVP에 호출·버튼 없음 |

유료 일괄 처리와 AI는 구매 의사, 지불 가능한 가격, 요청당 원가, 지원 비용을 확인한 뒤 판단한다. 실제 방문자·매출 자료가 없어 가격, 전환율, 손익분기점 또는 승인 확률을 제시하지 않는다.

## 4. 도구별 검색 유입과 연결

각 도구 URL은 실제 이용 가능한 도구와 그 도구에 맞는 짧고 정확한 설명을 함께 제공한다. 첫 HTML에서 제목·주요 본문·canonical이 보여야 하며 작업 시작에 JavaScript가 필요하다는 점도 명시한다. 결과·오류·빈 상태는 별도 색인 페이지를 양산하지 않는다.

| 도구 페이지 | 유입 의도 가설 | 고유한 도움 정보 |
| --- | --- | --- |
| 이미지 조절 | 사진 크기 또는 용량이 제한에 걸림 | 픽셀 크기·품질·용량의 차이, 원본 보존, 실제 변환 결과의 크기 표시 |
| 이미지 변환 | 제출처가 다른 이미지 형식을 요구 | 입력/출력 지원표, 투명도와 JPEG 배경, 변환할 수 없는 파일 안내 |
| PDF 합치기 | 여러 문서를 한 파일로 제출 | 순서 변경, 암호화 PDF 제한, 페이지·파일 크기 확인 |
| PDF 추출 | 필요한 페이지만 공유 | 페이지 범위 입력 예, 원본 비변경, 추출 결과 확인 |
| 이미지→PDF | 촬영 사진을 PDF로 제출 | 페이지 맞춤·여백·순서·방향이 결과에 미치는 영향 |
| 글자 수 | 지원서·소개글 등 글자 제한 확인 | 공백 포함/제외, 줄·단어 기준, 이모지·조합 문자 계산 기준 |

제목의 동의어만 바꾼 페이지를 늘리지 않는다. 지원 범위와 실동작이 다른 작업만 독립 URL로 만든다. 관련 NODELOG 글은 실제 독자 과업이 맞을 때만 연결하며 글 URL·canonical·hreflang·sitemap을 변경하지 않는다. 신규 `tools` 호스트는 자기 URL을 canonical로 두고 별도 sitemap에 **실제로 공개된** 페이지만 포함한다. 키워드 순위·검색량은 Search Console 데이터로 검증한다. Google의 [사람을 위한 콘텐츠 지침](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)은 독자에게 실제로 도움이 되는 내용과 고유한 가치의 점검을 권한다.

## 5. 비용 최소화 설계와 리스크

| 비용·리스크 | MVP 대응 | 실제 운영 때 확인할 값 |
| --- | --- | --- |
| Mac Studio CPU·메모리·스토리지 | 브라우저가 변환하고 Mac은 정적 HTML/JS/CSS만 제공. 업로드·변환 API·영구 파일 보관 없음 | 정적 origin 요청 수·대역폭, 응답 시간, PM2/Caddy·Tunnel 자원, 디스크 여유 |
| Cloudflare 트래픽 | 파일 바이트는 origin/Cloudflare를 통과하지 않도록 네트워크 시험. 해시가 붙은 JS/CSS/폰트는 긴 캐시 후보, HTML은 배포·롤백 속도를 고려해 짧은 캐시 후보 | `CF-Cache-Status`, 캐시 적중률, origin 요청량, 파일별 전송 크기, 배포 직후 구버전 혼합 여부 |
| PDF·이미지 라이브러리 | 필요한 도구 페이지에서만 라이브러리를 로드. 형식 지원과 번들 크기를 실제 측정해 라이브러리 선택 | 도구별 JS 다운로드 크기, 저사양 모바일 메모리·작업 시간, 파서 오류 |
| DB·외부 서비스 | 사용자 계정·저장·결제·AI API·신규 DB 없음. 분석은 필요 최소 이벤트와 기존 운영 자원 활용 여부를 먼저 검토 | 분석 제공자의 비용·개인정보 처리·동의 요구, 로그 보관량 |
| 사용자 지원 | 원본을 덮어쓰지 않고 사본 다운로드, 지원 형식·한계·오류 해결법을 도구 화면에 표시 | 실패 이유별 빈도, 문의량, 작업 이탈 원인 |
| 단일 호스트 장애 | 별도 앱·배포 산출물, 기존 서비스와 분리된 포트. 기술 로드맵 P0의 외부 백업·복원·빌드 분리 선행 | 가용성, 장애 복구 시간, 기존 서비스에 대한 영향 |

Cloudflare 공식 문서상 정적 JS/CSS 등은 기본 캐시 대상이지만 HTML은 기본적으로 캐시하지 않는다. 따라서 `tools` 호스트의 실제 프록시·Cache Rules·원본 헤더를 확인한 뒤 캐시를 설정한다. `www`, `game`, `moa`의 규칙을 일괄 변경하지 않는다: [Cloudflare 캐시 시작 안내](https://developers.cloudflare.com/cache/get-started/), [기본 캐시 동작](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/). 캐시가 적용돼도 Mac 원본 운영·장애 대비가 필요하다.

## 6. 수익 모델은 단계별 가설

1. **무료 도구→반복 사용:** 빠른 처리와 파일 비전송 안내가 재방문을 만든다는 가설. 최초에는 성공률·재방문을 먼저 확인한다.
2. **도구 설명 페이지의 광고:** 실제 내용과 작업 경험을 해치지 않는 위치에서 추가 수익이 가능한지 검토한다. 현재 MVP에는 광고 코드를 넣지 않는다. 장차 후보는 설명·사용법 아래 또는 관련 도구 영역 사이이며, 업로드/변환/다운로드 버튼 근처와 오류·완료만 있는 화면은 후보에서 제외한다. Google은 콘텐츠가 없거나 단순 행동 목적의 화면에 광고를 허용하지 않는다고 안내한다: [게시자 정책](https://support.google.com/publisherpolicies/answer/11112688?hl=en).
3. **고급 일괄 처리:** 반복 작업자의 시간 절약 가치가 실제 지불 의사로 이어지는지 인터뷰·테스트한다. 로컬 처리 한도를 무시하는 유료 약속은 하지 않는다.
4. **AI 부가 기능:** 비용과 유용성이 검증된 좁은 과업만 대상으로 한다. 현재 광고·AI·결제 구현은 범위 밖이다.

광고 도입 시 `tools.thivelab.com`의 사이트 등록·광고 범위·개인정보 고지와 지역별 동의를 계정에서 확인한다. EEA·영국·스위스 대상 맞춤형 광고는 Google의 [인증 CMP/TCF 요구사항](https://support.google.com/adsense/answer/13554116?hl=en)을 별도로 검토한다. 일반 배너만으로 충족한다고 가정하지 않는다. 광고 수익이나 승인 여부를 보장하지 않는다.

## 7. 사업 검증 지표와 수집 원칙

방문자 수와 작업 수는 다르다. 지표마다 기간·도구·기기 범주를 함께 보되 파일명, 파일 내용, 입력 텍스트, 이메일, 전체 URL 쿼리, 원본 오류 메시지는 이벤트에 보내지 않는다. 도구 코드·지원 형식 범주·정해진 오류 코드 정도만 허용한다. 재방문 식별과 교차 도메인 추적은 개인정보 고지·동의·분석 제품 설정을 검토한 뒤 구현하며, 구현 전에는 정확한 고유 사람 수를 주장하지 않는다.

| 지표 | 정의·측정 제안 | 판단에 쓸 질문 |
| --- | --- | --- |
| 자연검색 유입 | `tools` 호스트의 Search Console 노출·클릭·검색어·페이지별 추이. 분석의 유입 채널과 별도 대조 | 실제 과업 검색에서 어떤 페이지가 발견되는가? |
| 도구별 이용자 수 | 도구 페이지 방문 기기/브라우저 기준 추정 사용자와 세션, `tool_open` 수를 분리 표기 | 방문자가 실제 작업을 시작하는가? 중복 방문의 오차는 어느 정도인가? |
| 작업 시작률 | `job_start` / 유효 도구 페이지 방문 세션. 이미지·PDF는 파일 검증 통과 후, 글자 수는 첫 입력 후 시작으로 정의 | 설명·선택 단계에서 막히는가? |
| 완료율 | `job_success` / `job_start`; 별도로 `download_click` / `job_success`. 실패·취소를 분리 | 도구가 과업을 끝내는가, 결과를 실제 저장하는가? |
| 재방문율 | 동의 및 식별 기준이 정해진 경우에만 기간 내 재방문 추정 세션/사용자. 그렇지 않으면 추적 불가로 표시 | 한 번 쓰고 끝나는가, 다시 찾는가? |
| 관련 도구 이동률 | 한 작업 뒤 다른 도구 링크 클릭 세션 / 성공 세션. 실제 목적에 맞는 이동만 센다 | 연결이 후속 과업에 도움이 되는가? |
| 향후 광고 페이지뷰 | 광고 가능 콘텐츠 화면의 페이지뷰와 실제 광고 요청·노출을 분리. 오류·빈·완료 전용 화면 제외 | 광고가 UX·성능·완료율을 손상하는가? |
| 향후 유료 전환율 | 유료 기능이 출시된 뒤 `유료 결제 완료 고객 / 적격 제안 노출 사용자`를 기간별 표시. 환불·이탈 별도 | 사용자가 반복 작업의 가치에 돈을 지불하는가? |

최소 이벤트 후보: `tool_open`, `job_start`, `job_success`, `job_error`(정해진 코드), `job_cancel`, `download_click`, `related_tool_click`, `nodelog_referral`. 글자 수 도구는 입력할 때마다 이벤트를 보내지 않고 시작·명시적 복사 등 의미 있는 단계만 센다. 분석 구현 전에는 이벤트 스키마·보관·동의 요구를 확정한다. 검색 유입은 Search Console, 사용 흐름은 실제 선택한 분석 도구로 검증하며 서로 수치가 일치한다고 가정하지 않는다.

## 8. 의사결정 순서와 중단 기준

1. **P0 보호:** 기술 로드맵의 백업 복원·외부 백업·운영/DEV 빌드 분리·Cloudflare 실제 라우트 확인을 완료한다.
2. **소비자 과업 검증:** 6개 화면의 짧은 프로토타입으로 사용자에게 실제 파일·텍스트 작업을 맡겨 성공·오류·이탈 이유를 기록한다. 가상 고객 사례를 만들지 않는다.
3. **무료 MVP 개발:** 위 6개와 모바일·접근성·파일 비전송·정적 SEO 회귀 테스트를 통과시킨다. 텍스트 diff/JSON은 구현·노출하지 않는다.
4. **제한 공개 후 관찰:** 자연검색과 작업 퍼널을 기간별로 비교한다. 충분한 표본과 계절·유입 채널을 고려해 우선순위를 다시 정한다. 현재 자료가 없으므로 임의의 합격 방문자 수·전환율을 정하지 않는다.
5. **후속 수익 실험 결정:** 작업 성공률, 재방문, 관련 도구 이동, 문의 비용이 설명 가능한 수준인지 확인한 뒤 광고 또는 유료 가설을 각각 별도 실험 계획으로 승인한다. 완성되지 않은 기능이나 계정·동의 설정이 필요한 수익화는 출시하지 않는다.

**남은 확인:** 실제 일반 소비자 수요·검색어·유입 규모, 도구별 브라우저 호환성, 분석/광고 계정 설정, Cloudflare 캐시·트래픽 조건, 반복 사용자 지불 의사, 운영 지원 비용. 확인 전에는 매출 전망이나 손익분기점을 숫자로 제시하지 않는다.
